# Mobile product and safety boundary

The resident app lives in `apps/mobile`; the existing web app remains a demo and a prototype for a future responder workspace. The mobile app currently uses one public sample coordinate and cached GIS responses. It has no accounts, address entry, backend, live incident feed, push delivery, responder records, or route guidance. Its phone notification is a local test explicitly marked as a demo.

## Before real households or responders use it

1. **Identity and access.** Add resident sign-in through an established identity provider with verified email or passkey, account recovery, session revocation and rate limits. Require city-managed SSO and role-based authorization for responder access. Enforce ownership and role checks on the server for every read and write. The demo's public responder role selector is not an authorization mechanism. Verify parcel association before revealing property-specific records; never equate knowing an address with ownership.
2. **Sensitive household data.** Collect only fields that improve preparedness or response and obtain explicit, revocable consent for sharing with responders. Keep medical needs, access codes, floor plans, pets and precise addresses out of public bundles, analytics, logs and notification text. Encrypt transport and storage, limit staff access, record audited access, set a retention period and enable deletion and correction. Never transmit a location to a map or routing provider without informed consent.
3. **Maps.** For a selected property, query authoritative GIS layers on the server and return geometry, attributes, source URL and observation time. Draw actual polygons with a legend; distinguish hazard severity maps from live evacuation orders and show unavailable/stale layers. A marker by itself does not visualize a hazard boundary. Check provider terms and mobile map API key restrictions before release.
4. **Routes.** Let residents save their own exits, meeting places and household contacts. Show official evacuation zones and instructions first. A route can be suggested only when current official closures, evacuation directives, road graph, refresh timestamps and location accuracy are available; make uncertainty and alternative options visible. Never label a route safe based solely on static hazard polygons or infer indoor paths from unverified floor plans. Offline plans should remain viewable, but stale road data should not be presented as current routing.
5. **Alerts.** Start with official city enrollment. For FirePath remote push, arrange an authorized alert feed; validate publisher, signature or trusted transport, incident ID, issue/update/cancel state, expiry, geographic intersection and severity on the backend. Deduplicate, record delivery attempts, test cancellations and corrections, and avoid disclosing addresses in push payloads. Ask for notification permission in context and allow opt-out. Push is best effort and must not replace official alert channels. Remote push requires platform credentials, an app build and a server; a local test notification proves none of those connections.
6. **Responder workflow.** Prototype against fictional records. Integrate CAD or GIS only after city approval, data agreements, threat modeling and a verified least-privilege service boundary. Show a short dispatch summary with source/time and provide an audit trail. Never surface resident submissions as verified facts without provenance.

## Next implementation slice

Build resident address verification and protected profile storage, authoritative parcel and hazard lookup API, and a secure responder read path. Then integrate the city's approved alert feed and device token registration. Only after live closure and evacuation-zone sources are secured should route calculations enter testing. The ESP32 speaker remains an optional output channel and must follow the same verified event pipeline.
